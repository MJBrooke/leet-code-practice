Backpressure is a feedback mechanism allowing a system to signal to upstream producer that it
    is receiving data faster than it is consuming it
    -> It is a reactive signal
    -> Rate-limiting is a proactive signal

Problem
    Unbounded Queues: Producer can flood a queue with requests, leading to an indefinitely growing queue.
    Leads to:
        - Memory exhaustion: OOM
        - High latency: messages at back of queue take too long

Strategies
    - Control Producer
        Request only n items at a time by 'pull'
    - Dropping
        Discard incoming messages if not critical
        For non-essential telemetry or logging in peak times
    - Buffering
        Strict queue size
        When full, producer is blocked until slot opens
        Can lead to thread starvation
    - Shedding Load
        Using circuit breakers to return 503-ServiceUnavailable or 429-TooManyRequests

In Payment Context
    - Public API Gateway: uses rate-limiting (proactive backpressure) to return 429 errors
    - Internal microservices: bounded queues, with fail open/closed when full

---
Rate Limiting
    1. Token Bucket (burst friendly)
        Tokens added at fixed rate, requests use a token, if empty, reject request.
        Great for batching work.
    2. Leaky Bucket (Smooth choice)
        Imagine a bucket with a small hole. Requests are poured in at any speed, but 'leaks'
            at a consistent rate. If it overflows, requests are discarded.

HTTP with RL
    Include headers in response for clients to be smarter
    x-RateLimit-Limit: total allowance
    X-RateLimit-Remaining: token left
    Retry-After: timestamp of when to try again
